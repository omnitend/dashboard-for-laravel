# DXForm

The canonical form renderer. Drive it with field definitions; add `tabs` when
you need a multi-tab editor. Flat and tabbed forms share one engine
([DXField](/components/extended/DXField)), so every field type, conditional
field, per-field slot override, async option, and nested
[repeater](/components/extended/DXRepeater) works the same in both.

It works with the fetch-based `useForm` composable (no Inertia required) and
accepts either a `useForm` return or a `defineForm` return (with the latter,
`fields` may be omitted).

## Slots

Per-field slots are keyed by field key, e.g. `#value(price)` or `#hint(sku)`.

> **`#value` vs `#span`:** a *labelled custom control* is a normal field plus a
> `#value(<key>)` slot — it keeps the form's label column and grid, no
> re-derived col classes. Reserve `#span(<key>)` (with `span: true`) for
> genuinely full-width, label-less blocks (a sub-table, an activity log).

## Display-only values

In a horizontal row the label column is padded so its text lines up with the
text inside an input box. A row whose value has **no form control** (a badge, a
line of text, a link, a timestamp, a short list, a small table, a flex row of
text) needs nothing: the row is baseline-aligned, so the value's **first** line
of text sits on the label's, whatever markup you put in the slot:

```vue
<DXForm :form="form" :fields="fields" layout="horizontal">
  <template #value(connection)>
    <span class="badge text-bg-secondary">Not connected</span>
  </template>
</DXForm>
```

- A stack of lines aligns its first line; the rest follow below.
- A table aligns its first row's text; a badge is centred on the line.
- Inputs, selects, checkboxes, switches, radios, file inputs and buttons need
  nothing either. A row that holds any of them keeps the input alignment, so
  display text placed **above** a button sits at the top of the row; put the
  text beside the label in its own row instead.
- Content with no text at all (an image, an icon) puts its bottom edge on the
  label's baseline.
- `.dx-form-plaintext` (since 0.42.0) still works and is now redundant inside
  a horizontal form; a field with `plaintext: true` still wraps its
  `#value(<key>)` slot in it.

## Saved state

The submit button is a [DXSaveButton](/components/extended/DXSaveButton).
After a successful submit through the form's own methods (`form.post`,
`put`, `patch`…, read from `form.wasSuccessful`) it changes to a disabled
**✓ Saved** in the same navy (only the label and the disabled state change), and changing any field turns it back into the normal Save button.
While the request is in flight it shows the usual busy state
(`submitLoadingText`).

- Writes made by the save itself (an `onSuccess` that copies the response into
  the form, `resetOnSuccess`, or code straight after `await form.post()`) do
  not count as changes.
- An edit made while the request is in flight is not in the payload, so the
  button stays **Save** when that request succeeds.
- A failed save leaves the normal Save button.
- Forms that submit with something other than the form's own submit methods
  never see a success, so they keep the plain button. Set
  `:saved-state="false"` for a form whose submit is not a save, such as a
  search.

## Validation errors

When a submit through the form's own methods (`form.post`, `put`, `patch`…)
fails, DXForm lists **everything** the server returned in one alert, directly
above the submit button: a heading, then one row per validation message with
a readable label ("Price (line 1): Must be positive.").

- The heading is "Couldn't save. Please check:" (`errorSummaryTitle`) when
  the failure has field errors. Laravel's default 422 message (the first
  error plus "(and 3 more errors)") would only repeat the first row, so it
  is not shown then. A failure with no field errors (a message-only 422, a
  500, a network failure) is headed by the server's message.
- Rows for fields on the form come first, as buttons. Rows no visible field
  owns follow as plain text under "Other problems"
  (`errorSummaryOtherTitle`), a sub-heading shown only when both kinds are
  present.

- It is built from `form.submitFailure`, so it stays while the user edits
  (fixing a field does not remove its row or bring back a generic message)
  and disappears when the next submit starts or one succeeds.
- Keys with no rendered field, keys on hidden fields and message-only
  failures (`errors: {}`) are listed too, as plain text, so a 422 is never
  invisible.
- A row naming a visible field is a button: it selects the field's tab,
  scrolls to the field and focuses its input (for a repeater row, that row's
  field; a field's info button is never focused instead; an async editor is
  waited for). A `field(<key>)` slot is reached only if it binds the
  `targetAttrs` slot prop on the element holding its control
  (`<div v-bind="targetAttrs">…</div>`). The form looks for that marker
  when it needs it, anywhere inside the form (a `Teleport` into the form
  counts, one out of it does not), so content that marks itself after
  loading is found. When the row's field renders no marker (an unmarked
  slot), clicking the row still selects its tab and moves focus to the
  tab's button.
- A field taller than the window (a long explanation above its input) is
  scrolled by its input, centred, so the input is never left below the fold
  (by its first button when it has no input, such as a picker).
- The form also takes the user to the first problem: it selects the first
  tab holding an error (`autoErrorTab`) and scrolls the field into view
  (`scrollToError`), including on a `lazy` tab. A `preserveErrors` resubmit
  that returns the same errors does this again.
- While the summary shows a failure, the form-level alert does not render, so
  there is one alert, never two. `:error-summary="false"` turns the summary
  off and restores the old alert exactly; `error-summary="top"` puts it above
  the fields instead.

### Errors on nested keys (`errorKeys`)

An error key belongs to the field whose key equals it, or the field whose key
is a dot prefix of it (`lines.0.price` belongs to a `lines` repeater). A field
rendered under another name, such as a `span` field showing a custom order-line
editor, claims keys with `errorKeys`, where `*` matches one dot segment. Its
tab is then selected, its rows in the summary carry its label, and a row click
scrolls to it:

```ts
const fields: FieldDefinition[] = [
  { key: 'customer', type: 'text', label: 'Customer' },
  // A span field whose slot edits form.data.lines:
  { key: 'order_lines', type: 'text', label: 'Order lines', span: true,
    errorKeys: ['lines.*', 'lines.*.*'] },
];
const tabs: FormTab[] = [
  { key: 'general', label: 'General', fieldKeys: ['customer'] },
  { key: 'lines', label: 'Lines', fieldKeys: ['order_lines'] },
];
// A 422 with { "lines.0.price": ["Must be positive."] } selects "Lines".
```

### A summary outside the form

When the submit control lives outside DXForm (a modal footer, a sticky
action bar), set `error-summary="external"` and render
[DXFormErrorSummary](/components/extended/DXFormErrorSummary) beside the
button. Pass the form's own resolved rows (`errorTargets`) and let a row click
drive the form through its exposed `focusErrorTarget`, so the summary and the
form agree on every row. `"external"` tells DXForm another summary lists the
failure, so it renders neither its own summary nor its form-level alert
(`false` would bring that alert back for a message-only failure, or once the
last field error is fixed: two alerts). DXTable's create/edit modal does
exactly this.

```vue
<template>
  <DXForm ref="formRef" :form="form" :fields="fields" :tabs="tabs"
    :show-submit="false" error-summary="external" @submit="save" />

  <footer>
    <DXFormErrorSummary
      :form="form" :fields="fields" :tabs="tabs"
      :targets="formRef?.errorTargets ?? null"
      @select-target="formRef?.focusErrorTarget($event)"
    />
    <DButton variant="primary" @click="save">Save</DButton>
  </footer>
</template>

<script setup lang="ts">
import { ref } from 'vue';
import { DButton, DXForm, DXFormErrorSummary } from '@omnitend/dashboard-for-laravel';

const formRef = ref<InstanceType<typeof DXForm> | null>(null);
// form, fields and tabs as for any DXForm.
const save = () => form.post('/api/orders').catch(() => {});
</script>
```

## Container-driven layout

`layout="horizontal"` is unconditional, and that is a problem on a dashboard:
Bootstrap's breakpoints are **media** queries, so they only ever see the
*window*. A page narrowed by the persistent sidebar — or a form inside a modal —
can have very little room while the viewport is wide, and no breakpoint fires.
The label/input split then cramps the labels and truncates the controls.

`layout="auto"` measures the form's **own container** instead and stacks to
vertical below `layoutThreshold`:

```vue
<DXForm :form="form" :fields="fields" layout="auto" />
```

The default threshold is `640`px. With the default 45% label column, 640 leaves
the label ~275px of text and the control column ~341px. Raise `layoutThreshold`
if your controls need more room, or set a narrower `labelCols`.

Notes:

- `vertical` (the default) and `horizontal` are unchanged and unconditional. No
  existing form changes appearance; `auto` is opt-in.
- Before the first measurement — and when server-rendering — the form renders
  **vertical**. A stacked form is legible at any width, so it is the safe thing
  to show when the width is not yet known.
- The crossing has a small hysteresis band, so a form that gains a scrollbar
  when it stacks cannot flip back and forth at the boundary.
- Per-field `field.layout` still wins, and a `span: true` field is always
  full-width.

The measurement itself is available on its own — see
[useContainerWidth](/guide/forms#usecontainerwidth) if you need to drive
something else (a table that becomes cards, a column that collapses) off the
same signal.

## Field definitions

Each field is a `FieldDefinition`. Supported `type` values:

| Type | Renders |
| --- | --- |
| `text`, `email`, `password`, `number`, `url`, `tel`, `date`, `datetime-local`, `datetime`, `time` | Native input |
| `textarea` | Multi-line input |
| `select` | Dropdown (sync `options` or async `optionsLoader`). Add `searchable: true` for a type-to-filter select that still models the option's `value` |
| `autocomplete` | Free-text input with a `<datalist>` of suggestions (sync `options` or async `optionsLoader`); accepts values not in the list |
| `radio` | Radio group (single value from `options`) |
| `checkbox` | Single checkbox (boolean) |
| `checkbox-group` | Multiple checkboxes — "pick any of N" — from `options`; the model is an **array** of the checked option `value`s (default the field to `[]`) |
| `switch-list` | A list of labelled toggle rows (allergens, feature flags, opt-ins) from `options` — each row a real form-grid group with a compact track switch. Same array model as `checkbox-group`. `switchVariant: 'neutral'` is usually right for lists (a wall of red-off toggles over-signals); per-row extras via `#switch-list-item(<key>)` |
| `currency`, `percentage` | Numeric input with a `£`/`%` affix |
| `image`, `file` | File input (`image` shows a preview) |
| `component` | Renders your `field.component` (escape hatch) |
| `repeater` | Nested, repeatable sub-form (see [DXRepeater](/components/extended/DXRepeater)) |

Common options beyond `key`/`type`/`label`:
